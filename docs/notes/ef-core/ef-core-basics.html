EF Core 入門：從一個需求推到資料庫

不從名詞解釋開始，而是從「要做一個功能」出發，每遇到一個問題就引出下一個觀念：資料存哪裡 → .NET 怎麼跟資料庫溝通 → 為什麼需要 class → 為什麼需要 ORM → EF Core 怎麼運作 → 實際做一次。

0故事的開始

你接到一個任務

做一個部落格平台的後端 API：使用者可以開部落格、發文章、幫文章加標籤，讀者可以瀏覽文章。
明天主管會打開網站發一篇文章，後天再打開，那篇文章必須還在。

「發一篇文章」看起來很簡單：前端送來標題和內容，後端收下來就好。但「後天還要在」這句話會引出一連串問題，每解決一個就會冒出下一個。這份文件就照這個順序往下推：

1資料要存在哪裡？

先試最直覺的做法，看看哪裡不夠用。

嘗試一：放在程式的變數裡

var posts = new List<Post>();

app.MapPost("/posts", (Post post) => { posts.Add(post); return Results.Ok(); });
app.MapGet("/posts", () => posts);

可以運作，但 posts 存在記憶體裡。程式一重啟（重新部署、伺服器重開機、當機），文章就全部消失。不符合「後天還要在」。

嘗試二：存成檔案

每次發文就把整個清單寫進 posts.json。重啟後資料還在，但很快會遇到新問題：

  • 同時寫入：兩個人同時發文，後寫的覆蓋先寫的，有一篇不見了。
  • 查詢很慢：「找出標籤是 efcore 的文章」要把整個檔案讀進來一筆一筆比對，資料量一大就撐不住。
  • 寫到一半當機：檔案只寫了一半，整份 JSON 壞掉，所有資料都讀不出來。
  • 資料之間的關係：文章屬於哪個部落格、標籤被哪些文章使用，要自己維護、自己保證一致。

結論：交給資料庫

上面這些問題（保存、同時存取、快速查詢、不會寫一半、維護關係）正是資料庫專門解決的事。

需要的能力記憶體變數JSON 檔案關聯式資料庫
重啟後資料還在✗✓✓
多人同時寫入✗✗ 會互相覆蓋✓ 鎖定機制
大量資料中快速查詢—✗ 全部讀進來比對✓ 索引
寫到一半失敗不會壞掉—✗✓ 交易（Transaction）
保證資料之間的關係正確✗✗✓ 外鍵（Foreign Key）

關聯式資料庫用資料表（Table）存資料，長得像試算表：每一列（row）是一筆資料，每一欄（column）是一個欄位。

下一個問題資料庫和我們的 .NET 程式是兩個不同的東西，程式要怎麼把文章交給它？

2.NET 程式和資料庫是什麼關係？

它們是兩個獨立的程式，就像瀏覽器和網站伺服器一樣，透過網路對話。

重點只有三個：

要素說明比喻
連線字串資料庫在哪台機器、哪個資料庫、用什麼帳號登入地址 + 門禁卡
驅動程式（ADO.NET Provider）.NET 官方提供的連線元件，負責開連線、送出 SQL、接收結果。SQL Server 用 Microsoft.Data.SqlClient電話
SQL資料庫唯一聽得懂的語言。查詢用 SELECT，新增用 INSERT…雙方共通的語言

最原始的寫法：ADO.NET

.NET 內建的這套資料存取 API 叫 ADO.NET。把文章存進去、再讀出來：

using Microsoft.Data.SqlClient;

var connectionString = "Server=(localdb)\\mssqllocaldb;Database=Blogging;Trusted_Connection=True;";
using var conn = new SqlConnection(connectionString);
await conn.OpenAsync();                                                // ① 連線

// 寫入：自己組 INSERT
var insert = new SqlCommand(
    "INSERT INTO Posts (Title, Content, BlogId) VALUES (@title, @content, @blogId)", conn);
insert.Parameters.AddWithValue("@title", "EF Core 入門");              // 參數化，防 SQL Injection
insert.Parameters.AddWithValue("@content", "今天來介紹…");
insert.Parameters.AddWithValue("@blogId", 1);
await insert.ExecuteNonQueryAsync();                                   // ② 送出 SQL

// 讀取：自己組 SELECT，再一格一格讀
var select = new SqlCommand("SELECT PostId, Title, Content FROM Posts WHERE BlogId = @blogId", conn);
select.Parameters.AddWithValue("@blogId", 1);
using var reader = await select.ExecuteReaderAsync();                  // ③ 收回表格
while (await reader.ReadAsync())                                       // 一次讀一列
{
    var id    = (int)reader["PostId"];                                 // 用欄位名稱字串取值
    var title = (string)reader["Title"];                               // 自己轉型
}
記住這張圖

不管之後用什麼工具（包括 EF Core），底層永遠是這件事：送出 SQL 文字，收回表格資料。EF Core 本身就是建立在 ADO.NET 之上，它最後也是透過 Microsoft.Data.SqlClient 跟 SQL Server 說話。

下一個問題資料庫回來的是「一格一格的值」，但程式想處理的是「一篇文章」。這中間的落差怎麼辦？

3收回來的表格，程式要怎麼用？→ 需要 class

上一節的程式能動，但仔細看，寫起來到處是坑。

直接用欄位值的問題

問題例子後果
欄位名稱是字串reader["Tilte"] 打錯字編譯會過，執行到那行才爆炸
型別要自己轉把 bigint 欄位轉成 (int)執行時 InvalidCastException
資料散成一堆變數id、title、content 各自獨立無法當成「一篇文章」傳給其他方法、回傳給前端
不知道一筆資料有哪些欄位要翻資料庫才知道 Posts 有什麼欄位沒有自動完成，容易漏

解法：先定義「一篇文章長什麼樣子」

用 class 描述資料的形狀，資料表的一列就對應到一個物件：

資料庫：資料表 Posts 
CREATE TABLE Posts (
    PostId   int IDENTITY PRIMARY KEY,
    Title    nvarchar(200) NOT NULL,
    Content  nvarchar(max),
    BlogId   int NOT NULL
);
C#：class Post 
public class Post
{
    public int PostId { get; set; }
    public string Title { get; set; }
    public string Content { get; set; }
    public int BlogId { get; set; }
}

讀取時把每一列「裝進」一個物件，之後整個程式都用物件溝通：

var posts = new List<Post>();
while (await reader.ReadAsync())
{
    posts.Add(new Post                       // 一列 → 一個 Post 物件
    {
        PostId  = reader.GetInt32(0),
        Title   = reader.GetString(1),
        Content = reader.IsDBNull(2) ? null : reader.GetString(2),   // NULL 也要自己處理
        BlogId  = reader.GetInt32(3),
    });
}
return posts;                                // 可以直接回傳、序列化成 JSON

class 的目的

目的說明
描述資料結構屬性 = 欄位，型別 = 欄位型別（int → int、string → nvarchar、DateTime? → 可為 NULL 的 datetime2）
型別安全post.Tilte 打錯字 → 編譯錯誤，IDE 直接標紅
把相關資料綁在一起「一篇文章」是一個東西，可以傳給方法、放進 List、回傳給前端
表達關係之後可以加上 public Blog Blog，用 post.Blog.Url 取代手寫 JOIN
名詞：Entity / POCO

對應到資料表的 class 稱為 Entity（實體）。它不需要繼承任何特殊類別，就是普通的 class，所以也叫 POCO（Plain Old CLR Object）。

下一個問題有了 class，讀取變好用了，但上面那段「一列裝進一個物件」的程式碼，每張表、每個查詢都要再寫一次。還有更多麻煩的事…

4每次都手寫 SQL 和轉換，太累了 → 需要 ORM

把目前「ADO.NET + class」的做法套到整個部落格平台，看看還剩下多少重複的苦工。

還沒解決的苦工

情境ADO.NET + class 要做的事
新增一個查詢寫 SQL 字串 + 加參數 + 寫一段「一列 → 物件」的轉換
改了文章標題要存回去自己記得哪些屬性改過，組出 UPDATE Posts SET Title = @t WHERE PostId = @id
讀部落格順便帶出所有文章寫 JOIN，再把攤平的結果手動組回「Blog 底下有 List<Post>」
class 加了一個屬性自己寫 ALTER TABLE，還要記得每台環境的資料庫都要執行
同時新增文章和標籤自己開交易、依序 INSERT、出錯時自己 Rollback

你會發現：class 已經描述了資料的形狀，這些 SQL 和轉換其實都能從 class 推導出來。既然能推導，就交給工具自動做。這種工具叫 ORM（Object-Relational Mapper，物件關聯對映）。

同一件事，有沒有 ORM 的差別

ADO.NET + class 
var cmd = new SqlCommand(
    "SELECT PostId, Title, Content, BlogId " +
    "FROM Posts WHERE BlogId = @id", conn);
cmd.Parameters.AddWithValue("@id", 1);
using var reader = await cmd.ExecuteReaderAsync();
var posts = new List<Post>();
while (await reader.ReadAsync())
    posts.Add(new Post
    {
        PostId  = reader.GetInt32(0),
        Title   = reader.GetString(1),
        Content = reader.GetString(2),
        BlogId  = reader.GetInt32(3),
    });
EF Core 
var posts = await db.Posts
    .Where(p => p.BlogId == 1)
    .ToListAsync();

// 改標題並存回：EF 自己知道要 UPDATE 哪個欄位
posts[0].Title = "新標題";
await db.SaveChangesAsync();
苦工EF Core 怎麼處理
寫 SQLLINQ 自動轉譯成 SQL，預設參數化（防 SQL Injection）
一列 → 物件自動實體化（Materialization）
判斷改了什麼、組 UPDATEChange Tracker 自動比對
JOIN 後組回物件Include(b => b.Posts)
改表結構Migration 依 class 產生，並保留版本紀錄
交易一次 SaveChanges 就是一個交易

.NET 常見的三種選擇

ADO.NETDapper（Micro-ORM）EF Core（完整 ORM）
SQL 誰寫自己自己自動產生（也可自己寫）
結果 → 物件手動✓✓
變更追蹤✗✗✓
Migration✗✗✓
執行效能最快接近 ADO.NET稍慢（多一層轉譯與追蹤）
開發速度慢中快
適合極致效能、底層工具複雜報表、手調 SQL以 CRUD 與商業邏輯為主的應用（例如我們的部落格平台）
ORM 不是魔法，也有代價

效能開銷：多了轉譯與變更追蹤。純讀取時可加 AsNoTracking()。

產生的 SQL 不一定最好：最常見的是 N+1 問題，在迴圈裡讀導覽屬性，每筆都多發一次查詢。解法是用 Include 或 Select 一次載入。

還是要懂 SQL：記得第 2 節的圖，底層仍是送 SQL、收表格。把 log 等級調高就能看到 EF 實際送出的 SQL（見第 12 節）。

可以混用：EF Core 也能執行自寫 SQL（FromSqlInterpolated），同一個專案也能搭配 Dapper 使用。

下一個問題決定用 EF Core 了。它內部由哪些零件組成？一個查詢、一次存檔，背後到底發生了什麼？

5EF Core 的組成

ORM 是一種概念，EF Core 是 .NET 官方的實作。把第 2 節的圖放大，看 EF Core 插在你的程式和驅動程式之間做了哪些事。

角色負責什麼對應資料庫
Entity資料的形狀一張 Table
DbContext一次工作階段（Unit of Work）：查詢入口、追蹤變更、SaveChanges() 一次寫入整個資料庫
DbSet<T>DbContext 上的屬性，查詢與新增的入口一張 Table
Provider把 EF 的指令翻成特定資料庫的 SQL（SqlServer、Npgsql、Sqlite…）資料庫種類
連線字串資料庫在哪裡、怎麼登入連線資訊
Migration比對 class 的變化，產生建表 / 改表的程式碼Schema 版本

6class 如何對應資料表

以官方範例 Blog、Post、Tag 為例，看 C# 這端和資料庫那端各長什麼樣子。

觀察重點

導覽屬性不會變成欄位：Blog.Posts、Post.Blog 只存在 C# 端，資料庫只有外鍵 Posts.BlogId。

多對多會多一張中間表：C# 兩邊各放一個 List，EF Core 5 以上會自動建立 PostTag。

主鍵慣例：名為 Id 或 <類別名>Id 的屬性會自動成為主鍵，int 主鍵預設為自動遞增。

7一次查詢在背後發生什麼

以 GET /blogs 查出網址含 "dotnet" 的部落格為例。

延遲執行（Deferred Execution）

Where、OrderBy 只是在組裝查詢，不會連資料庫；直到 ToListAsync()、FirstAsync()、CountAsync() 等「取值」方法才真正送出 SQL。

8一次寫入在背後發生什麼

DbContext 會記住你對物件做了什麼（Change Tracking），呼叫 SaveChanges 時才一次寫入。

Entity 狀態何時出現SaveChanges 時
Added呼叫 Add()INSERT
Unchanged剛查詢出來 / 剛存檔完不做事
Modified改了屬性值UPDATE（只更新有變的欄位）
Deleted呼叫 Remove()DELETE
Detached不受 DbContext 追蹤不做事

10情境：一份需求

原理都懂了，回到第 0 節的任務。動手前先把「做一個部落格平台」寫成明確的需求單，接著走一次 需求 → 分析 → 實作 → 驗收。

需求單 · 小型部落格平台 API

我們要做一個部落格平台的後端。使用者可以開自己的部落格、發文章，文章可以加標籤，讀者可以依標籤找文章。

  1. R1使用者可以建立部落格，部落格要有網址，網址不可重複。
  2. R2每個部落格可以發表多篇文章。文章有標題（必填，最多 200 字）、內容、發布時間（沒給就用現在時間）。
  3. R3文章可以加上多個標籤，同一個標籤可以用在多篇文章，標籤名稱不可重複。
  4. R4刪除部落格時，底下的文章一併刪除。
  5. R5需要的 API：查某部落格的文章列表（新到舊）、依標籤查文章、新增文章時可同時給標籤（標籤不存在就建立）。

11需求分析：從文字到模型

不要急著寫程式。先把需求拆成四個問題，每個問題的答案剛好對應到 EF Core 的一塊。

① 找名詞：哪些是 Entity，哪些只是屬性？

把需求裡的名詞圈出來。判斷原則：它自己有沒有身分（需要被單獨查詢、被多個東西引用）？有的話就是 Entity，沒有的話只是某個 Entity 的屬性。

名詞判斷理由
部落格Entity：Blog可以被建立、刪除，底下掛著文章
文章Entity：Post可以被列出、新增，有自己的標籤
標籤Entity：TagR3「同一個標籤用在多篇文章」→ 被多個東西共用，要有自己的身分；R5 要依標籤查詢
網址屬性：Blog.Url描述部落格，不會單獨存在
標題、內容、發布時間屬性：Post.Title / Content / PublishedOn描述文章
標籤名稱屬性：Tag.Name描述標籤
常見的猶豫：標籤可以只是一個字串欄位嗎？

如果寫成 Post.Tags = "csharp,efcore"，就無法保證 R3「名稱不可重複」，R5「依標籤查詢」也只能用 LIKE 模糊比對，又慢又不準。只要需求裡出現「共用」或「依它查詢」，通常就該獨立成 Entity。

② 找關係：幾對幾？

對每一對 Entity 問兩次「一個 A 有幾個 B？一個 B 有幾個 A？」

關係A → BB → A結論實作方式
Blog ↔ Post一個部落格有多篇文章（R2）一篇文章屬於一個部落格一對多Post 放外鍵 BlogId；Blog 放 List<Post>
Post ↔ Tag一篇文章有多個標籤（R3）一個標籤用在多篇文章（R3）多對多兩邊各放 List，EF 自動建中間表
Blog ↔ Tag沒有直接關係（透過文章間接相關）不用設定

③ 找規則：每條限制對應哪個設定？

把需求中的「必填、最多、不可重複、一併刪除、預設」這類字眼挑出來，逐條翻成 EF Core 設定。

需求規則EF Core 設定資料庫結果
R1網址必填、不可重複IsRequired() + HasIndex(b => b.Url).IsUnique()NOT NULL + UNIQUE INDEX
R2標題必填、最多 200 字IsRequired().HasMaxLength(200)nvarchar(200) NOT NULL
R2發布時間預設現在HasDefaultValueSql("getutcdate()")DEFAULT getutcdate()
R3標籤名稱不可重複HasIndex(t => t.Name).IsUnique()UNIQUE INDEX
R4刪部落格一併刪文章OnDelete(DeleteBehavior.Cascade)（必填外鍵的預設值，寫出來讓意圖清楚）ON DELETE CASCADE
為什麼「不可重複」要交給資料庫？

程式先查再新增（AnyAsync 後 Add）時，兩個請求同時進來還是可能都通過檢查。唯一索引才是最後一道保證。程式端的檢查是為了回傳友善的錯誤訊息。

④ 找操作：要查什麼、寫什麼？

需求API查詢重點
R1POST /blogs先檢查網址是否存在 → 回 409 Conflict
R4DELETE /blogs/{id}Remove 部落格，文章由資料庫串聯刪除
R5GET /blogs/{id}/postsWhere(BlogId) + OrderByDescending(PublishedOn)，用 Select 只取需要的欄位
R5GET /tags/{name}/posts多對多查詢：Where(p => p.Tags.Any(t => t.Name == name))
R5POST /blogs/{id}/posts找出已存在的標籤 + 建立新標籤，一次 SaveChanges 寫入
API 不要直接回傳 Entity

Blog.Posts → Post.Blog → Blog.Posts… 導覽屬性會互相指來指去，序列化成 JSON 時會丟出 A possible object cycle was detected。用 Select 投影成匿名物件或 DTO：只回需要的欄位，SQL 也只查那些欄位。

12實作：從零連接資料庫

依分析結果動手，環境為 .NET 6 Minimal API + SQL Server LocalDB。程式中的 // R1 等註解標示對應的需求。

  1. 安裝 NuGet 套件

    在 .csproj 所在資料夾執行，版本跟 .NET 同一大版號：

    dotnet add package Microsoft.EntityFrameworkCore.SqlServer --version 6.0.*
dotnet add package Microsoft.EntityFrameworkCore.Design --version 6.0.*
    套件用途
    Microsoft.EntityFrameworkCore.SqlServerEF Core 本體 + SQL Server Provider
    Microsoft.EntityFrameworkCore.Design讓 dotnet ef 讀取專案、產生 Migration

  2. 安裝 dotnet-ef 命令列工具

    dotnet tool install --global dotnet-ef --version 6.*
dotnet ef --version

  3. 準備資料庫

    選項適合連線字串範例
    SQL Server LocalDBWindows 本機開發，免設定Server=(localdb)\mssqllocaldb;Database=Blogging;Trusted_Connection=True;
    SQL Server（Docker）跨平台、接近正式環境Server=localhost,1433;Database=Blogging;User Id=sa;Password=…;TrustServerCertificate=True;
    SQLite最輕量，一個檔案Data Source=blogging.db（套件改用 …Sqlite，呼叫 UseSqlite；getutcdate() 要改成 SQLite 的寫法）

    確認 LocalDB：執行 sqllocaldb info 應看到 MSSQLLocalDB。

  4. 撰寫 Entity（分析 ① ②）

    Models/Blog.cs 
    public class Blog
{
    public int BlogId { get; set; }                     // 主鍵（慣例：<類別名>Id）
    public string Url { get; set; }                     // R1

    public List<Post> Posts { get; set; } = new();      // R2 一對多
}
    Models/Post.cs 
    public class Post
{
    public int PostId { get; set; }
    public string Title { get; set; }                   // R2
    public string Content { get; set; }
    public DateTime PublishedOn { get; set; }           // R2

    public int BlogId { get; set; }                     // 外鍵
    public Blog Blog { get; set; }                      // 導覽屬性

    public List<Tag> Tags { get; set; } = new();        // R3 多對多
}
    Models/Tag.cs 
    public class Tag
{
    public int TagId { get; set; }
    public string Name { get; set; }                    // R3

    public List<Post> Posts { get; set; } = new();      // R3 多對多的另一端
}

  5. 建立 DbContext（分析 ③）

    Data/BloggingContext.cs 
    using Microsoft.EntityFrameworkCore;

public class BloggingContext : DbContext
{
    public BloggingContext(DbContextOptions<BloggingContext> options) : base(options)
    {
    }

    public DbSet<Blog> Blogs { get; set; }
    public DbSet<Post> Posts { get; set; }
    public DbSet<Tag> Tags { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Blog>(eb =>
        {
            eb.Property(b => b.Url).IsRequired().HasMaxLength(500);   // R1 必填
            eb.HasIndex(b => b.Url).IsUnique();                       // R1 不可重複

            eb.HasMany(b => b.Posts)                                  // R2 一對多
              .WithOne(p => p.Blog)
              .HasForeignKey(p => p.BlogId)
              .OnDelete(DeleteBehavior.Cascade);                      // R4 一併刪除
        });

        modelBuilder.Entity<Post>(eb =>
        {
            eb.Property(p => p.Title).IsRequired().HasMaxLength(200); // R2 必填、200 字
            eb.Property(p => p.PublishedOn)
              .HasDefaultValueSql("getutcdate()");                    // R2 預設現在
            eb.HasIndex(p => p.PublishedOn);                          // R5 依時間排序常用

            eb.HasMany(p => p.Tags).WithMany(t => t.Posts);           // R3 多對多
        });

        modelBuilder.Entity<Tag>(eb =>
        {
            eb.Property(t => t.Name).IsRequired().HasMaxLength(50);
            eb.HasIndex(t => t.Name).IsUnique();                      // R3 不可重複
        });
    }
}
    建構子接收 options 的原因

    連線字串和使用哪個資料庫由外部（DI 註冊時）決定，DbContext 本身不寫死。這樣測試時可以換成別的資料庫，例如 SQLite in-memory。

  6. 設定連線字串

    appsettings.json 
    {
  "ConnectionStrings": {
    "BloggingDb": "Server=(localdb)\\mssqllocaldb;Database=Blogging;Trusted_Connection=True;"
  }
}
    注意

    JSON 裡的反斜線要寫成 \\。含密碼的連線字串不要 commit，開發時用 User Secrets：dotnet user-secrets set "ConnectionStrings:BloggingDb" "…"。

  7. 註冊 DbContext 到 DI

    Program.cs 
    using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<BloggingContext>(options =>
    options.UseSqlServer(builder.Configuration.GetConnectionString("BloggingDb")));

var app = builder.Build();

    AddDbContext 預設是 Scoped，也就是每個 HTTP request 各一個實例。DbContext 不是 thread-safe，不要註冊成 Singleton。

  8. 建立 Migration 並更新資料庫

    dotnet ef migrations add InitialCreate
dotnet ef database update
    產生的檔案內容
    <時間戳>_InitialCreate.csUp() 建表、Down() 還原
    <時間戳>_InitialCreate.Designer.cs該版本的模型 metadata
    BloggingContextModelSnapshot.cs目前模型的完整快照，下次新增 Migration 時拿來比對

    打開 InitialCreate.cs 的 Up()，可以對照分析 ③：應該看得到 maxLength: 200、defaultValueSql: "getutcdate()"、onDelete: ReferentialAction.Cascade、unique: true。Migration 檔要 commit 進版本控制。

  9. 實作 API（分析 ④）

    Program.cs（接在 var app = builder.Build(); 之後） 
    // R1 建立部落格，網址不可重複
app.MapPost("/blogs", async (BloggingContext db, CreateBlogRequest req) =>
{
    if (await db.Blogs.AnyAsync(b => b.Url == req.Url))
        return Results.Conflict($"網址 {req.Url} 已被使用");

    var blog = new Blog { Url = req.Url };
    db.Blogs.Add(blog);                                // 標記為 Added
    await db.SaveChangesAsync();                       // 送出 INSERT，取回 BlogId
    return Results.Created($"/blogs/{blog.BlogId}", new { blog.BlogId, blog.Url });
});

// R4 刪除部落格，文章由資料庫 ON DELETE CASCADE 一併刪除
app.MapDelete("/blogs/{blogId:int}", async (int blogId, BloggingContext db) =>
{
    var blog = await db.Blogs.FindAsync(blogId);
    if (blog is null) return Results.NotFound();

    db.Blogs.Remove(blog);
    await db.SaveChangesAsync();
    return Results.NoContent();
});

// R5 某部落格的文章，新到舊
app.MapGet("/blogs/{blogId:int}/posts", async (int blogId, BloggingContext db) =>
    await db.Posts
        .AsNoTracking()                                // 只讀，不需追蹤
        .Where(p => p.BlogId == blogId)
        .OrderByDescending(p => p.PublishedOn)
        .Select(p => new                               // 投影：只取需要的欄位，避免循環參考
        {
            p.PostId,
            p.Title,
            p.PublishedOn,
            Tags = p.Tags.Select(t => t.Name)          // 在 Select 中讀導覽屬性，不需 Include
        })
        .ToListAsync());

// R5 依標籤查文章（多對多）
app.MapGet("/tags/{name}/posts", async (string name, BloggingContext db) =>
    await db.Posts
        .AsNoTracking()
        .Where(p => p.Tags.Any(t => t.Name == name))
        .OrderByDescending(p => p.PublishedOn)
        .Select(p => new { p.PostId, p.Title, BlogUrl = p.Blog.Url })
        .ToListAsync());

// R2 + R3 + R5 新增文章，同時給標籤（不存在就建立）
app.MapPost("/blogs/{blogId:int}/posts", async (int blogId, CreatePostRequest req, BloggingContext db) =>
{
    if (!await db.Blogs.AnyAsync(b => b.BlogId == blogId))
        return Results.NotFound();

    var names = req.Tags.Distinct().ToList();
    var existingTags = await db.Tags
        .Where(t => names.Contains(t.Name))            // 轉成 SQL 的 IN (...)
        .ToListAsync();
    var newTags = names
        .Except(existingTags.Select(t => t.Name))
        .Select(n => new Tag { Name = n });

    var post = new Post { BlogId = blogId, Title = req.Title, Content = req.Content };
    post.Tags.AddRange(existingTags);                  // 已存在：只建立關聯
    post.Tags.AddRange(newTags);                       // 不存在：INSERT Tag + 關聯

    db.Posts.Add(post);
    await db.SaveChangesAsync();                       // 同一個交易寫入 Posts、Tags、PostTag
    return Results.Created($"/posts/{post.PostId}", new { post.PostId });
});

app.Run();

record CreateBlogRequest(string Url);
record CreatePostRequest(string Title, string Content, List<string> Tags);
    看 EF 實際送出的 SQL

    在 appsettings.Development.json 的 Logging:LogLevel 加上 "Microsoft.EntityFrameworkCore.Database.Command": "Information"，就能在主控台對照上面的時序圖。

13驗收：逐條對照需求

開 Swagger 實際打 API，每條需求都要能指出「在哪裡實作」和「怎麼證明」。

需求實作位置驗證方式預期結果
R1唯一索引 + POST /blogs 檢查同一個網址建立兩次第二次回 409 Conflict
R2Title 的 IsRequired().HasMaxLength(200)、PublishedOn 預設值新增文章不給發布時間；標題給 201 字發布時間自動填入；超長標題寫入失敗
R3多對多 + Tag.Name 唯一索引兩篇文章都用標籤 efcoreTags 只有一筆 efcore，PostTag 有兩筆
R4OnDelete(Cascade)刪除有文章的部落格該部落格的文章也消失，PostTag 對應列一併刪除
R5三個 Endpoint依序呼叫列表新到舊；依標籤查得到；新標籤自動建立
R2 的長度驗證只靠資料庫還不夠

標題超過 200 字時，SQL Server 會拒絕寫入，EF 丟出 DbUpdateException，API 會回 500。正式專案要在進資料庫前先驗證輸入，例如檢查 req.Title.Length 或使用 FluentValidation，然後回 400 Bad Request。資料庫的限制是最後一道防線。

需求變更時怎麼辦？

假設之後新增需求「R6：文章要記錄瀏覽次數」，就照第 9 節的循環走一次：

  1. 分析：瀏覽次數是 Post 的屬性，不是新的 Entity → 加 public int ViewCount { get; set; }
  2. 規則：預設 0 → HasDefaultValue(0)
  3. dotnet ef migrations add AddPostViewCount → 檢查 Up() 只有 AddColumn
  4. dotnet ef database update，舊資料自動補上 0

14設定規則：慣例與 Fluent API

EF Core 先套用「慣例（Convention）」，再用 Data Annotations 或 Fluent API 覆寫。

常見慣例

慣例效果
屬性名為 Id 或 <類別名>Id成為主鍵；int / long 會自動遞增
屬性名為 <導覽屬性名>Id，型別與對方主鍵相同成為外鍵
兩邊都有集合導覽屬性多對多，自動建立中間表
可為 null 的型別（int?、DateTime?）欄位允許 NULL
DbSet 屬性名稱資料表名稱

Data Annotations 與 Fluent API

Data Annotations：寫在 class 上 
public class Blog
{
    public int BlogId { get; set; }

    [Required, MaxLength(500)]
    public string Url { get; set; }
}
Fluent API：集中在 DbContext 
modelBuilder.Entity<Blog>()
    .Property(b => b.Url)
    .IsRequired()
    .HasMaxLength(500);

兩種方式可以混用，衝突時 Fluent API 優先。Fluent API 能設定的東西比較多，例如刪除行為、精度、預設值 SQL，而且 Entity 能保持乾淨，所以設定多的時候建議集中寫在 Fluent API。

常用 Fluent API

方法效果
HasKey(x => x.Code)指定主鍵
IsRequired()NOT NULL
HasMaxLength(n)nvarchar(n)
HasColumnType("varchar(200)")直接指定 SQL 型別
HasColumnName("X")欄位名稱
HasPrecision(18, 2)decimal 精度
HasDefaultValue(v) / HasDefaultValueSql("getutcdate()")預設值
HasIndex(x => x.Url).IsUnique()唯一索引
HasOne / HasMany / WithOne / WithMany設定關聯
OnDelete(DeleteBehavior.Restrict)刪除行為（Cascade、Restrict、SetNull、NoAction）

15Migration 指令速查

指令用途
dotnet ef migrations add <名稱>依模型變更新增 Migration
dotnet ef database update套用到最新版本
dotnet ef database update <名稱>退回或前進到指定 Migration
dotnet ef migrations remove刪除最後一個、尚未套用的 Migration
dotnet ef migrations list列出 Migration 及是否已套用
dotnet ef migrations script產生 SQL 腳本（部署到正式環境用）
dotnet ef database drop刪除整個資料庫（開發時重來用）
dotnet ef dbcontext scaffold "<連線字串>" Microsoft.EntityFrameworkCore.SqlServerDatabase First：從現有資料庫產生 class
套用前先看 Up()

出現 DropColumn 或 DropTable 代表資料會消失。屬性改名時，EF 可能誤判成「刪掉舊欄位、新增新欄位」，這時要手動改成 RenameColumn。

錯誤訊息原因解法

The Entity Framework tools version 'X' is older than that of the runtime 'Y'工具與套件版本不一致dotnet tool update --global dotnet-ef --version 6.*
A network-related or instance-specific error occurred…連不到資料庫確認 sqllocaldb info、連線字串、JSON 中的 \\
A possible object cycle was detectedAPI 直接回傳含導覽屬性的 Entity，JSON 序列化時循環參考用 Select 投影成匿名物件 / DTO（見第 11 節）
Cannot insert duplicate key row ... with unique index違反唯一索引（例如重複網址）寫入前先檢查並回 409；資料庫索引是最後防線
